## The short version

- Supabase is a Postgres platform. Every project is a Postgres database, with auto-generated REST
  and GraphQL APIs, auth, storage, Edge Functions and a realtime channel layered on top.
- Concile is a reactive backend. You write TypeScript functions. Every query is live. Authorization
  is code. The database is a detail you pick with a flag.
- Supabase wins on the Postgres ecosystem and on being a hosted product. Concile wins on live
  queries, on authorization you can unit test, and on running as one process.

## Side by side

| | Concile | Supabase |
| --- | --- | --- |
| Live results from your own server code | Yes, read-set precise | Partly, row change events |
| Backend is plain TypeScript functions | Yes, query, mutation, action | Partly, Edge Functions off to the side |
| Authorization is ordinary code, not a rules language | Yes, functions you can unit test | No, row-level security in SQL |
| Self-host the whole product | Yes, one process, one command | Partly, several composed services |
| Single binary with no database to run | Yes | No, Postgres required |
| Swap the database without touching app code | Yes, SQLite or Postgres | No, Postgres only |
| Durable workflows with rollback | Yes, saga compensation | No, bring your own |
| Offline writes that survive a reload | Yes, durable outbox | No |
| Full-text and vector search | Not built yet | Yes, tsvector and pgvector |
| Hosted cloud | None | Yes |
| Price | Free to self-host | Free tier; Pro from $25 per month; Team from $599 per month; compute billed per project on top |

## Live query versus change feed

Supabase Realtime is three primitives: Broadcast for messages between clients, Presence for who is
online, and Postgres Changes, which streams row events off the database. A row event tells you a
row changed. It does not tell you whether that row still belongs in the filtered, joined, sorted
list your screen is showing. Anything beyond "watch this whole table" is the client's job to work
out.

In Concile, the query is the subscription. The server records what the query read, notices when a
commit touches it, re-runs it, and pushes the current, correct result. The client never
re-derives anything. This is what "realtime by default" means.

## Authorization: code versus SQL policies

Supabase authorization is Postgres Row Level Security: policies written in SQL, one per operation
per table, enforced by the database on every access. Supabase's own docs describe what makes that
hard to get right. A table in an exposed schema without RLS enabled is readable and writable by any
role with a grant. Views bypass RLS unless `security_invoker` is set. Two tables whose policies
reference each other raise a recursion error. Supabase recommends a pgTAP test file per protected
table, because there is no other way to know the policies do what you meant.

In Concile, authorization is a function. It runs in the same transaction as the read or write, it
is type-checked with the rest of your app, and you unit test it like anything else. Row policies
are available through `@concile/authz` if you want them composed for you.

## Deploying it yourself

Supabase's core is open source and self-hostable with Docker Compose or the CLI, Studio included.
What you run is Postgres plus the services around it: PostgREST, pg_graphql, Realtime, GoTrue for
auth, Storage, Studio. Each is a process to keep alive and upgrade.

Concile is one process. `docker compose up` starts the engine, the database and the dashboard. Or
`concile build` and ship one executable. It also runs on Cloudflare Workers.

## Where Supabase is ahead

- It is Postgres. Decades of tooling, standard SQL, 40-plus preinstalled extensions, and no
  vendor query language.
- Auto-generated REST and GraphQL APIs from your schema, with no code to write for a plain CRUD
  API.
- Search. Full-text through tsvector and vectors through pgvector are built in. Concile has
  neither yet.
- A hosted product in 16-plus regions with SOC 2 Type 2, and compute tiers up to 64 vCPU and
  256 GB on a single published tier.

## Where Concile is ahead

- Live queries computed on the server, not row events for the client to interpret.
- Authorization as code, in the transaction, under the type checker.
- One process to run instead of a ring of services.
- SQLite when you want zero config, Postgres when you want Postgres. Same app code.
- Durable workflows with compensation and a durable offline outbox, built in.
- No connection caps or compute bills. Supabase caps realtime peak connections at 200 on Free and
  500 on Pro and Team, with $10 per additional 1,000, and bills compute hourly per project on top of
  the plan.

## Moving from Supabase

There is no migration tool, because the model changes: functions replace PostgREST calls plus RLS
policies. Your data is portable. Export it from Postgres, define the same tables in `schema.ts`,
and import with `concile migrate import`. Each RLS policy becomes an `if` in the function that
reads or writes that table, which is usually shorter than the policy was.

## When to pick Supabase

You want Postgres and its ecosystem as the centre of the system, a hosted product with regions and
compliance today, and search built in. You are comfortable writing and testing SQL policies.

## When to pick Concile

You want every screen to update on its own without writing the invalidation logic, authorization
you can read and test as code, and a backend you run as one process anywhere.
